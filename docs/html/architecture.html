The processes

Every process is the same meritorder command (and the same image, except the compressor's). The gateway, worker and controller follow the stored configuration in Postgres, so a change saved on the console reaches all of them; the compressor takes only its command-line flags.

Process Command Needs How many
Gateway meritorder serve (port 8080; MERITORDER_PORT) Nothing for a trial (in-memory storage); Postgres and Redis for anything shared As many as you like; --workers N (or MERITORDER_WORKERS) for more processes on one machine, which needs Postgres and Redis
Migrations meritorder migrate Postgres Once per upgrade (Compose's migrate service; the chart's migrate Job, migrations.enabled)
Worker meritorder worker (a cycle every 60 s, --interval; --metrics-port, or MERITORDER_WORKER_METRICS_PORT, for its /metrics) Postgres (it refuses to start without it), Redis One or more: batch jobs and eval runs are claimed with a lease, so several share them
Capacity controller meritorder controller (every 60 s; --interval) Postgres (it refuses to start without it), Redis; SkyPilot or a Kubernetes cluster for the GPUs it runs One active: the others wait on a Postgres advisory lock. Compose's gpu profile; the chart's controller.enabled
Compressor meritorder compressor (port 8090) The compressor extra (LLMLingua-2, torch); its own image Optional. Compose's compressor profile, the chart's compressor.enabled; gateways call it at MERITORDER_COMPRESSOR_URL

Without Postgres there's no worker. A gateway on in-memory storage then checks its own batches every 15 seconds and deletes stored responses past their retention itself.

Why it's split this way

  • Gateway is stateless so it scales horizontally behind any load balancer and can be restarted freely.
  • Controller is separate because its decisions are slow (minutes) and the gateway's are fast (milliseconds). The controller only changes what exists; the router only chooses among what exists.
  • GPU pool is optional. With no GPUs configured, the system is a cost-aware API gateway, and still useful. A vLLM/SGLang server you already run can be added without SkyPilot (provisioner: static), and a Kubernetes cluster with GPUs can run vLLM through KServe or llm-d (provisioner: kubernetes).

Backend adapters: pass-through first

Merit Order has its own adapter layer instead of depending on LiteLLM (see 09: Decisions, decision 2). It stays small because almost every backend speaks one of two formats:

Format Backends
Anthropic Messages Anthropic, Claude on Bedrock (its Anthropic-compatible endpoint), Claude on Vertex, Claude on Foundry
OpenAI-compatible OpenAI (through its Responses API: api: responses), Azure OpenAI, Gemini on Vertex AI (its OpenAI-compatible endpoint, or Gemini's native API: api: gemini), the Gemini API (native: api: gemini), OpenRouter, xAI, DeepSeek, Mistral, Moonshot, Z.ai, MiniMax, vLLM, SGLang, most others
Later, if needed Bedrock Converse
  • Pass-through keeps fidelity. Fields we don't recognize (cache_control, thinking signatures, encrypted reasoning, provider extras) reach the backend exactly as the harness sent them. That is what keeps prompt caching working.
  • Translation is one pair of converters (OpenAI Chat Completions ⇄ Anthropic Messages), unit-tested in both directions, streams included. The Responses API is converted to and from Chat Completions at the edges: for clients that call /v1/responses, and for OpenAI backends set to api: responses. Gemini's native API is converted the same way, at the backend, for backends set to api: gemini (below).
  • Provider auth uses official libraries: botocore for AWS request signing, google-auth for Vertex, azure-identity for Entra ID (Foundry, Azure OpenAI).
  • Long tail: any OpenAI-compatible endpoint is a valid backend. Anyone who needs a niche provider can run LiteLLM (or anything else) themselves and register it as a backend, out of process.

Gemini's native API

Gemini also answers on OpenAI-compatible endpoints (Vertex AI's, OpenRouter's), but those drop or flatten what Gemini's own API reports. A backend with format: openai and api: gemini calls generateContent and streamGenerateContent?alt=sse instead, while the rest of the gateway keeps seeing Chat Completions (formats/gemini_upstream.py, GeminiBackend in backends/http.py):

Where Config Auth
The Gemini API base_url: https://generativelanguage.googleapis.com/v1beta auth: {type: api_key, header: x-goog-api-key, value_env: GEMINI_API_KEY}
Vertex AI flavor: vertex, project, region (global by default) auth: {type: google}, as for Claude on Vertex

The shipped config has both: gemini, on once GEMINI_API_KEY is set, and vertex-gemini-native, off until MERITORDER_VERTEX_GEMINI_NATIVE=true (on Vertex, the OpenAI-compatible vertex-gemini stays the default for now). A route's model is Gemini's id (gemini-4-carbon); google/… and models/… work too. Prices come from LiteLLM's list (gemini/… for the Gemini API, vertex_ai/… for Vertex), like any direct provider API.

Replies and streams come back as Chat Completions: text, function calls, thought summaries as reasoning_content, and usageMetadata as usage (cached tokens from cachedContentTokenCount; thinking counts as output, and is also shown as reasoning_tokens). Finish reasons:

Gemini says The gateway sees
STOP (tool_calls when the reply calls functions), MAX_TOKENS stop / tool_calls, length
A blocked prompt (promptFeedback.blockReason), or SAFETY, RECITATION, PROHIBITED_CONTENT, BLOCKLIST, SPII, … content_filter with a refusal saying why: a refusal, which auto retries on another model
MALFORMED_FUNCTION_CALL, MALFORMED_RESPONSE An error (502): the request goes to the next source
MISSING_THOUGHT_SIGNATURE An error (400), returned to the client
PUP_LIMITED_DISABLED (the Google account is restricted) 403: the next backend
HTTP 429 (RESOURCE_EXHAUSTED) and 503 (UNAVAILABLE) Capacity: the request moves on, and that model is skipped on that backend for a while (after a 429, for the retryDelay Google gives in the error's details)

Gemini 3 and later return a thought signature with each step's first function call and reject a request whose current-turn call comes back without one. The signature rides on the tool call as extra_content.google.thought_signature, the convention of Google's own OpenAI-compatible endpoint, so a client that sends messages back as it got them keeps Gemini's reasoning between tool calls (an OpenRouter reasoning_details signature is used too). A call with none (a client that rebuilt its history, a translated Anthropic request, a call another model made) is sent with Google's documented bypass value, so the request still works; the model just reasons afresh.

Hot-path budget

The gateway should add single-digit milliseconds before the first byte goes upstream. Everything on the hot path is in-memory or one Redis round trip:

Step Where it reads from
Key validation In-process cache (60 s), Postgres on miss
Rate limit / budget Redis counters (a missing spend counter is seeded from the Postgres ledger)
Session lookup Redis, in the same round trip as the counters
GPU state and headroom Published to Redis by the controller; each gateway reloads deployment state every 5 s and reads utilization with the session
Token estimate In-memory: one pass over the request's text (sampled above 256K characters, about 5 ms for 4 MB), corrected per model by this process's calibration
Classifier Rules; only on new sessions and task boundaries
Learned router (opt-in) In-memory, pure Python, at the same points: hashing the ends of the latest prompt and six dot products, about 0.4 ms at the p99 on a long agent prompt. Its row (hashed features, no content) is written with the ledger row, after the response
Judged labels (opt-in per team) At the team's sample rate (1%): a reference to the request's body is held, and the answer kept as text once it's complete. After the response, in the background, the replay on a stronger model and the judging run as requests of their own (the team's internal client, judged-labels:<team>); the client never waits. Only the verdict is written (03)
Compression The rules: deterministic and in-memory. Model-based: one Redis round trip for every result's stored decision; a result new on this turn waits for the compressor service at most the team's deadline_ms (1,000), then goes as it is

Writes to Postgres (usage, ledger) are async and never block the response.

Nothing unusual. Same API it already speaks, streamed tokens, usage numbers. Response headers tell curious users what happened:

A chained Responses API turn (stored mode)

For a team with stored responses on (04, decision 51), a client of OpenAI's Responses API can send only its new input with previous_response_id. This is where the gateway holds conversation content: sealed in Postgres, for the team's retention. The turn is rebuilt into the stateless request it amounts to before anything else happens, so the pipeline above runs on it unchanged.

The client's input is stored as it sent it, before compression, so the next turn rebuilds the same history and compression's stored decisions apply to it the same way. A stream is kept just before its response.completed event goes out, since a client may chain the moment it sees it. If keeping it fails, the client still gets the answer (a non-streamed one says store: false) and meritorder_stored_responses_total{event="failed"} counts it. Conversations (conversation) work the same way, from the conversation's items, and add the turn's input and output to it. background: true keeps the response as queued and answers at once; the same steps run in that gateway, and the client polls GET /v1/responses/{id}.

What Where Until
Each stored response: the object as the client got it, and the input sent with it Postgres (stored_responses), sealed with MERITORDER_RESPONSES_KEY retention_days after the chain's last turn, or the response, its owner, or their team's stored mode is deleted
Each conversation's metadata and items Postgres (stored_conversations, conversation_items), each sealed retention_days after it last changed, or it or its owner is deleted
Owner, chain, status, where it ran, the provider's response id, item ids, sizes the same rows, in the clear with them
A provider's copy (backends with responses_store only) the provider (OpenAI: at least 30 days) deleted there when the gateway deletes its own

A Responses API turn over WebSocket

Codex CLI keeps one WebSocket open to /v1/responses (04, decision 54) and, from its second turn, sends only the new items with previous_response_id. Without stored mode the gateway holds the conversation for the connection only, in memory, and each turn becomes the stateless request it amounts to, so the pipeline above runs on it unchanged.

A previous_response_id that isn't this stream's latest gets previous_response_not_found, and Codex sends everything. In stored mode a stored response chains as in the section above, from any connection. Closing the connection drops what it held and stops a running turn (ledger status 499).

Responses API tools on any backend

A Responses API turn becomes a Chat Completions request inside the gateway, and from there goes to any backend. Plain function tools carry over as they are. The other kinds, which Codex CLI sends, are translated both ways (formats/responses_tools.py, decision 57), as OpenAI's Responses reference and Codex CLI's source (codex-rs, 15 November 2026) define them:

A backend with api: responses gets the tools and the items as the client sent them, additional_tools merged into tools, since the public API takes tools there. Over WebSocket a turn has no response headers: the log line is all that says a tool was left out.

Translating between API formats

When the client and the backend speak the same API, the request passes through untouched. When they don't, formats/translate.py (Chat Completions and Anthropic Messages), formats/responses.py (the Responses API, on top of Chat Completions) and formats/responses_upstream.py (Chat Completions to a backend with api: responses) convert the request and the reply. The tests check each direction against the official openai and anthropic Python SDKs: the streams accumulate in the SDKs' own stream handlers and the objects validate as the SDKs' types (tests/test_api_fidelity.py). Followed: Anthropic's Messages, PDF support, tool use, thinking and preserved thinking docs, and OpenAI's Chat Completions and Responses references, November 2026.

Nothing the request carries is dropped without a word: content goes across in the other API's own form, or the request is refused with a 400 that says why.

Batches: work that can wait

Every provider here charges less for requests that can wait up to 24 hours (about half): summarizing a backlog, labelling a dataset, nightly evals. A GPU deployment that's already running does them for almost nothing while it has room. Clients send them the way they would to the provider, and Merit Order routes each request on its own, splits the batch across providers and GPUs, and joins the results back.

Each line can name a model or use auto. X-Route-Floor, X-Route-Hint and X-MeritOrder-Tags on the create call apply to every line.

Routing a batch

Each request is routed like a live one, with these differences: only routes whose backend has a batch API qualify, and running GPU deployments with room; provider routes are priced at batch prices for that one request (the prompt at the batch input price, plus its max_tokens, or the router's usual reply size when it sets none), and GPU routes at their shadow price for their load now; there's no session to keep warm; and speed doesn't count, since nobody is waiting. So a named model goes to its cheapest route, and auto gives the request its level, takes the models at that level the team may use, and picks the cheapest of their routes. Team policies (allowed_models, allowed_backends), the per-request cost limit (at batch prices) and cost per success apply as they do live. Rate limits and the per-session spend cap don't: they're for live load, and a batch isn't a session. Merit Order adds no cache markers to batch requests (there's no next turn to read them); the client's own are passed on. With the learned router on, a batch request is leveled as a new live task is (the learned level in route mode, when it's sure), but it records nothing for the router to learn from: no retry, raised floor or stopped stream can follow it (03).

A request that nothing allows is refused on its own, with the reason in the batch's error file (or as an errored result), and the rest go ahead; a batch where no request can go is refused outright. Refused requests never reached a provider, so, like a live refusal, they aren't in the ledger. Requests then go into jobs: one per backend, and per model where the provider takes one model a job (OpenAI, Azure, Moonshot, Mistral, OpenRouter, Gemini, Bedrock, Vertex AI), split within each provider's limits. A group smaller than a provider's minimum (Bedrock's 100 records) moves to its requests' next routes. A job a provider refuses moves to its requests' next routes once; what still can't go is refused with every route's reason.

Batch work on your GPUs

A GPU deployment that's running is paid for by the hour, whatever it does, so a request that can wait costs it almost nothing while it has room (05, 10). The router prices a batch request on a running deployment at its shadow price for its load now: 2% of the GPU route's price (its API-equivalent rate) while it's below the knee (routing.shadow_knee, 60%), rising toward the full price as it fills. Against the providers' batch prices (about half), a GPU with room wins, for the model the request names, or for auto a model at or above its level (a free upgrade, as live). A deployment that's full, draining, stopped or still starting isn't a route. The request's next route with a provider batch API is kept as its fallback, shaped for that provider at once, so the worker can hand it on without routing it again (Bedrock isn't a fallback: its jobs need 100 requests).

The requests can't wait at a provider, so the gateway holds them, sealed (below), and the worker runs them, a slice of a minute at a time while it holds the job's lease:

  • Only in the headroom. Batch requests fill a deployment up to the knee of max_concurrency × replicas, never past it, counting the gateways' live requests there and other workers' batch requests (each published to Redis every couple of seconds), and none while vLLM's own load, less the batch work it's running, is at the knee. So batch work never makes live traffic pay more than the shadow price's floor. Live routing doesn't count batch requests as load: they give way. A deployment without max_concurrency takes no batch work, since its free slots can't be counted.
  • Live traffic first. Each request goes to vLLM with priority: 20 (batches.gpu.priority; lower runs first), after free upgrades (10) and live requests (0). vLLM's priority scheduler preempts batch requests when live ones need the room.
  • Before the deadline. What hasn't run 12 hours after the batch was made (batches.gpu.handoff_hours) goes to its fallback's batch API (providers finish most batches in minutes to a few hours). So does everything still waiting when the deployment stops, starts draining or leaves the configuration, and a request the GPU refuses (a 4xx) or fails twice. A request with no fallback (a model only on your GPUs) waits for the GPU until the batch's deadline, then expires; one the GPU can't run fails with the GPU's error.
  • The client's deadline holds. A provider gives the handed-on job a fresh 24-hour window, which would end after the client's. So the worker checks a handed-on job again at the batch's deadline at the latest, cancels it there if it's still running, and what the provider hadn't run comes back expired (504), as from a provider whose window closed; what it ran is kept and billed. For that, a GPU's fallback is always a batch API the gateway can cancel: OpenRouter's has no cancel, so it's never one (the next route with a batch API is used, or none). Past the deadline nothing is handed on: what's still waiting for the GPU expires.
  • No GPU starts for it. Batch work doesn't count toward starting or keeping a deployment: the break-even controller sizes GPUs on live demand only, and batch work only uses what that pays for (decision 49).

Each request settles as soon as it's run: its result is held, then its ledger row is written (service_tier: batch, backend the GPU), priced as live GPU work is, by the GPU time its tokens took at the deployment's hourly price. Its savings split in two: the batch discount, what a provider's batch API would have taken off the model's API price (the fallback's batch price, else the usual half), and self-hosting, what the GPU took off that batch price (negative if the GPU time cost more). What's reserved against budgets is the fallback's estimate, since the request may end up there. The batch object's meritorder.providers counts requests where they are now, so a handed-on request moves from the GPU to its provider.

Prices and spend

A route's batch price is the live price list's (LiteLLM's *_batches prices, cache prices included where listed), else the standard price less the provider's published batch discount (the table above; batch.discount changes it), or a price.batch written on the route for a negotiated rate. Long-prompt tiers move with the input price.

  • Reserved when submitted. The batch's estimated cost must fit every budget it counts against (organization, team, person), counting what's already spent and what running batches have reserved. A batch that doesn't fit is refused with 429, saying which budget and what's left. The estimate is then added to the month's spend counters, so live requests and other batches see it. A counter seeded from the ledger adds what running batches have reserved.
  • Settled from the results. The worker writes one ledger row per request when its job ends (service_tier: batch, batch_id), priced at the batch price the job was submitted at, and moves that request's estimate off the reservation. The row is stamped when it's written, so a job settled late (its results couldn't be read for a while) lands in the month whose spend counters count it, and in the hours the rollups look at again. GPU requests settle one by one, as they run. Failed, cancelled and expired requests get a row with their status (499 cancelled, 504 expired, else the provider's) and no cost. What's left of a reservation is released when the batch ends.
  • Savings. The batch discount is its own cause (savings_batch): the served model at its live API price less the same tokens at its batch price. Routing savings are counted against live prices, as for any request, so the discount never shows up as routing. A client using a provider's batch API directly would get the same discount, which is why it's kept apart. On a GPU, what the GPU took off the batch price is self-hosting's (savings_self_hosting), as for live GPU work.

Without MERITORDER_BATCH_KEY a gateway on Postgres refuses uploads (503, saying why) and sends no batch work to GPUs (it goes to the providers); Anthropic-style batches to providers need no key. An in-memory gateway (development) uses a random key for the life of the process. Deleting an OpenAI batch's output or error file, or an Anthropic batch (DELETE /v1/messages/batches/{id}), deletes its results at the providers (and what's held for its GPU work) at once. Results a provider no longer has (Gemini's files last 48 hours) come back as errors saying so. A batch belongs to the person who made it: others get 404; admins can see and cancel it, but not read or delete its results.

In your bucket. batches.storage.bucket holds uploads and GPU work in an S3 bucket, a Cloud Storage bucket or an Azure Blob Storage container instead of Postgres, sealed all the same: large uploads stay out of the database, and the bucket's own retention and encryption rules apply on top. Requests are signed with the credentials the backends use: those of the backend batches.storage.backend names, else of the first enabled backend that signs in to that cloud (aws_sigv4, google, azure_ad), else that cloud's default credentials (the AWS chain, Application Default Credentials, Entra ID's for https://storage.azure.com/.default). A file uploaded before the setting changed is read from where it was put, as long as that's still the storage bucket (or Postgres); the console says how many are held elsewhere.

Rotating the key while uploads wait. Every sealed piece names the key that sealed it (an 8-byte id derived from the key, not the key). To rotate, set the new key in MERITORDER_BATCH_KEY and the old one in MERITORDER_BATCH_KEY_PREVIOUS (or batches.previous_key_file) on every gateway and worker. New content is sealed with the new key; what the old one sealed stays readable for batches.key_grace_days from when a gateway or worker first used the new key (recorded in the store, so all count from the same moment). The default is the retention period plus two days, the longest anything sealed before the rotation is kept (a batch's window, a fallback provider's, then retention), so nothing is lost if the old key is simply left set that long. After that the old key isn't read: content still sealed with it says so. Reports → Batches and meritorder batch storage show the key ids, until when the old one is read, and how many uploads still need it. Content from before key ids existed is tried with each key.

The worker

Jobs are claimed from Postgres with a lease per job (FOR UPDATE SKIP LOCKED, as eval runs are), so several workers share them, and one that dies mid-job hands it on when its lease runs out (15 minutes). The first check comes batches.poll_seconds (60) after a job is submitted, and the wait doubles while nothing changes, up to max_poll_seconds (1,800). Provider errors back off the same way, honoring Retry-After, and alert after five in a row. A job the provider no longer knows (404) fails its requests at no cost. The gateway gives a provider 20 minutes to take a job (counted from when it starts sending it, not while it waits its turn), then counts it as refused. A job still "submitting" 30 minutes after that start (the gateway stopped before the provider answered) fails too, and a provider job it may have made isn't tracked. Settling reads the results once, in chunks of 500, each in one transaction with its ledger rows, so a restart picks up where it stopped. A GPU job is worked on a slice at a time and asked again within seconds while it has requests and the deployment has room (15 seconds when it has none); the worker follows the GPUs' state as the gateways do, from what the controller publishes. Without Postgres there's no worker, and the gateway checks on its own batches every 15 seconds.

Metrics. The worker counts each request it settles in Prometheus counters of its own, meritorder_batch_requests_total (by model, backend, the API that ran it, and status), meritorder_batch_tokens_total, meritorder_batch_cost_usd_total, meritorder_batch_baseline_usd_total and meritorder_batch_savings_usd_total (by cause), plus meritorder_batch_gpu_requests_total, meritorder_batch_handoffs_total and meritorder_batch_poll_errors_total, served on MERITORDER_WORKER_METRICS_PORT (meritorder worker --metrics-port; 9464 in Compose and the Helm chart) at /metrics, behind MERITORDER_METRICS_TOKEN when it's set. Nothing is counted twice: a request is counted only by the call that settles it (the database marks it settled in the same transaction), and only in the batch counters, never in the gateways' live ones, so adding the two gives all spend (08). Without Postgres the gateway settles its own batches and serves the same counters on its /metrics.

Batch statuses, in OpenAI's words: in_progress, cancelling, finalizing (the providers are done; results are being settled), completed, cancelled (what ran before it stopped is kept and billed), expired (a provider, or a GPU for a request with no other route, didn't run everything in its window; what ran is kept and billed) and failed (no provider accepted it). Anthropic's processing_status is in_progress, canceling or ended. OpenRouter has no cancel: a cancelled batch there runs to its end, and what ran is billed.

Inside, a batch is in_progress, finalizing or ended with an outcome (batches/poller.py); the OpenAI and Anthropic objects are made from that. A batch whose jobs all end with nothing left to settle goes straight to its outcome.

  retention_days: 7               # then results at the providers, in buckets and held for GPUs are deleted, and unused uploads

  previous_key_env: MERITORDER_BATCH_KEY_PREVIOUS   # after a rotation, read for key_grace_days (or previous_key_file)
  key_grace_days: 9               # default: retention_days + 2

Written from the providers' references, November 2026

Every provider call is tested against fakes shaped like the providers' API references as read on 13 November 2026: Anthropic Message Batches (anthropic-version as the backend sets it, else 2023-06-01), OpenAI's v1 Batch and Files APIs, Azure OpenAI's v1 API, Moonshot's batch guide (platform.kimi.ai), Mistral's batch API (and its Python SDK 3.7.0 for what the reference leaves out), xAI's batch API reference, OpenRouter's batch API guide, the Gemini API v1beta (batch mode and asyncBatchEmbedContent; the Python SDK 3.3.0 still calls batch embeddings experimental), Bedrock's batch inference API, Vertex AI v1, and the S3, Cloud Storage JSON v1 and Azure Blob Storage REST APIs (x-ms-version 2025-11-05). These still need checking with real accounts:

  • Anthropic: the content type of the results download (the SDK asks for application/binary).
  • OpenAI: whether cancelled requests come back in the error file as batch_cancelled (only expired ones are documented), and the exact shape of a request that failed with 4xx or 5xx (both shapes are read).
  • Azure: the batch's endpoint spelling on the v1 API (/chat/completions is sent; lines call /v1/chat/completions), the dotted expires_after.* form fields, Responses API lines, and its timestamps (some examples show ISO strings).
  • Moonshot: whether 24h is accepted as well as 1d (1d is sent), the per-file request limit (none is published), and how files are deleted (OpenAI's DELETE /v1/files/{id} is sent).
  • Mistral: the shape of a failed line in its error file (OpenAI's is read), and DELETE /v1/batch/jobs/{id}, which is in its SDK but not its reference (a 404 or 405 is fine).
  • xAI: which models are discounted (20% is assumed for every route without a listed batch price), and whether a batch with requests still pending after its expire_time reports them as cancelled.
  • OpenRouter: whether a batch variant is named by the plain model id (it's sent as the route's model, or batch_model), and the error type of an expired request.
  • Gemini API: whether output lines echo key, the shape of an error line, how long output files last, and for embeddings which token count a line carries (usageMetadata.promptTokenCount or tokenCount; either is read, else 0).
  • Bedrock: the S3 layout of the outputs (the gateway lists the job's folder), the recordId rules, and whether bedrock-mantle model ids are what batch inference takes (else set batch_model).
  • Vertex AI: Claude's output line format, and whether a Gemini request's labels (where the key rides) are echoed.
  • GPUs: that a vLLM server preempts priority: 20 requests for live ones as its priority scheduler documents (--scheduling-policy priority, which Merit Order's provisioners set; a static server without it refuses the field, and its batch requests go to their fallbacks).
  • Buckets: Azure's x-ms-date with an Entra token, and S3 regions other than the backend's (set batches.storage.region).

Looked at and not built: Bedrock's OpenAI-compatible batch API (on bedrock-runtime, for OpenAI's gpt-oss models only, which no Bedrock route here serves, with the same S3 input as batch inference); Vertex AI has no OpenAI-compatible batch endpoint (its batch prediction for open models takes OpenAI-format input lines, but its output format isn't documented); Azure's embeddings batches (its docs list no embedding model for batch deployments); Z.ai (its international API has no batch API; Zhipu's BigModel in China has one, at a different address), DeepSeek and MiniMax (none).

Not built: embeddings batch work on self-hosted GPUs; re-sealing held content with a new key (the grace period covers everything sealed before a rotation instead); Gemini batch embeddings on Vertex AI.
